How a 7B model learned to diagnose application logs.

LogSage is a QLoRA adapter built on Qwen2.5-7B-Instruct. It turns raw application logs into a structured first-pass diagnosis with an issue, likely root cause, severity, fix, and confidence.

The complete story

Dataset contract → QLoRA training → adapter publishing → Colab inference.

This page follows the same sequence used in the video. Every number and link comes from the repository, training report, or published Hugging Face adapter. No synthetic benchmark theatre, because the actual workflow is already interesting enough.

01

Dataset

Teach a stable response contract.

Each row pairs raw logs and an instruction with a structured output containing issue, root_cause, severity, fix, and confidence. Dataset validation normalizes severity and confidence before training.

1,116validated rows
02

Formatting

Turn every example into a Qwen conversation.

The project uses ChatML-style system, user, and assistant turns. Training and inference must use the same conversation structure, otherwise the adapter is asked to perform a task in a dialect it was not trained on.

5required output fields
03

QLoRA

Freeze the quantized base and train small adapter weights.

The 7B base model is loaded in 4-bit form. LoRA rank 16 adapters capture task-specific updates while the original model remains separate. The result is a portable PEFT adapter rather than another full 7B checkpoint.

r=16LoRA rank
04

AWS training

Run the real job on one NVIDIA A10G.

The training run used an AWS EC2 g5.2xlarge, three epochs, 378 steps, checkpointing, TensorBoard, JSONL metrics, evaluation outputs, and cost controls.

34.3mtraining runtime
05

Publishing

Push the adapter to Hugging Face.

The published repository stores the task-specific adapter and metadata. Inference still needs the compatible Qwen base model. Base model plus adapter produces LogSage behavior.

PEFTportable adapter
06

Inference

Load everything in a fresh Google Colab runtime.

Colab proves the adapter can be reproduced away from the training machine: install dependencies, load the tokenizer and 4-bit base, attach the adapter, apply the chat template, generate, decode only new tokens, then extract and validate JSON.

The actual training run

The model improved, then the evaluation signal flattened.

Training loss alone is not proof of usefulness. The best evaluation loss was 0.789 at step 250; the final evaluation loss was 0.811. That is evidence of learning, not a substitute for schema-validity, hallucination, latency, and held-out task benchmarks.

The only live build in the video

Fresh Colab runtime, base model, adapter, structured output.

LogSage_Inference_Colab.ipynb
# 1. Load tokenizer + 4-bit Qwen base
base = AutoModelForCausalLM.from_pretrained(...)

# 2. Attach published LogSage adapter
model = PeftModel.from_pretrained(base, adapter_id)

# 3. Reuse the training chat structure
prompt = tokenizer.apply_chat_template(messages, ...)

# 4. Generate only the diagnosis
outputs = model.generate(...)
answer = outputs[0][input_length:]

# 5. Decode and validate structured JSON
result = extract_json(tokenizer.decode(answer))

What viewers should understand

The tokenizer applies the model's conversation format. The base model supplies general language capability. The PEFT adapter supplies LogSage's learned task behavior. Generation produces text, so post-processing still has to extract and validate the expected schema.

The honest boundary

A focused experiment, not an incident authority.

LogSage can produce a useful first hypothesis, but it may hallucinate root causes, miss cross-service context, mishandle unseen formats, or sound more certain than the evidence supports.

The current project does not claim a complete production benchmark. Stronger evaluation still needs held-out cases, JSON-validity rate, base-model comparison, latency measurement, hallucination analysis, and confidence calibration.
