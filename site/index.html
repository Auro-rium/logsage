The chronology

A focused model, built as a full engineering workflow.

The point was never to make a generic chat assistant. The point was to take an incident-shaped input, teach a model a stable response contract, run the training on real hardware, measure it, and leave behind artifacts another engineer can inspect.

01

Dataset discipline

Start with a contract, not a prompt.

Each training row paired an instruction and raw log context with a required response shape: issue, root_cause, severity, fix, and confidence. Validation normalized severity labels and confidence percentages before training began.

1,116validated examples
02

Prompting for the model

Format the task as a Qwen conversation.

The dataset was converted into ChatML-style system, user, and assistant turns. That gives Qwen a consistent role structure while keeping the final answer anchored to a JSON-style incident diagnosis.

5required response fields
03

Cloud execution

Use QLoRA to fit the project on one GPU.

Instead of updating every parameter in the 7B base model, the run trained low-rank adapter weights on a 4-bit quantized base. That made the experiment practical on a single AWS g5.2xlarge with an NVIDIA A10G GPU.

24 GBA10G VRAM
04

Observability

Watch the curve, not just the final number.

Training logged checkpoints, JSONL metrics, TensorBoard events, evaluation generations, and a report. The goal was to make the learning behavior inspectable rather than treating the training command as a black box.

378optimization steps
05

Artifact handoff

Publish the adapter, keep the base separate.

The final PEFT adapter, tokenizer, evaluation outputs, and model card were published to Hugging Face. Colab and local inference load the base model first, then attach the adapter.

PEFTadapter publishing
06

Cost control

Back up the run, then stop the meter.

Final artifacts were pulled down locally before the training instance was terminated. The project deliberately used an eight-hour termination guard and cleanup checks for leftover EBS volumes.

Real observability

A training job should leave evidence behind.

The TensorBoard run captured the same questions an engineer asks when a model begins to learn: Is loss moving? Is evaluation holding steady? Are there signs of instability? Is the job actually using the GPU we paid for?

  • Console and file logs for execution traceability
  • Metrics JSONL for programmatic analysis
  • Checkpointing every 25 steps for recovery
  • Sample generations for qualitative inspection

How it is used

Base model + adapter + a strict response contract.

inference.py
# 1. Load the 4-bit Qwen base
base = load("Qwen2.5-7B-Instruct")

# 2. Attach LogSage LoRA weights
model = attach_adapter(base, "LogSage-Qwen2.5")

# 3. Give it logs + context
raw = model.generate(chat_prompt(logs))

# 4. Extract and validate structured JSON
diagnosis = validate(extract_json(raw))

Why the JSON layer matters

Language models can echo prompts or wrap an otherwise useful answer in commentary. The inference path extracts the assistant JSON, checks required keys, normalizes severity, and ensures confidence is consistently represented.

The honest boundary

Useful as an assistant, not an authority.

LogSage is a small, focused v0 adapter. It can form a useful first hypothesis, but it can also hallucinate root causes, miss cross-service context, or sound more certain than the evidence supports.

Real operational use needs redaction, PII handling, source-aware context, calibrated confidence, human review, and audit logging around the model.

The takeaway

The model is small. The workflow is the project.

LogSage is an applied LLM engineering story from data contract to cloud GPU to published adapter. The interesting part is not only that it can summarize a failure. It is that the training, measurement, cost controls, and handoff can all be traced.
